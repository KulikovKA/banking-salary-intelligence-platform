# ADR-006 — Разделить допуск офлайн-разработки и live-ingestion

**Статус:** APPROVED WITH CHANGES владельцем проекта, 2026-10-10; условия G0-LIVE не выданы ни для одного банковского источника.\
**Дата:** 2026-10-09; редакция по review Astra и решению владельца от 2026-10-10.\
**База:** архитектура v1.1 остаётся принятой; ADR меняет допуски, граф разработки и правила evidence.

## Контекст

SRC-001/WORK-01 остаётся BLOCKED: не подтверждены банковские разрешения и применимые условия для автоматического сбора; текущих employer tariff originals для требуемого покрытия нет. Это блокирует live-ingestion и приёмку реальных тарифов, но не независимое проектирование и тестирование POC. WORK-02 уже имеет 15 успешных Python-тестов; это технический прогресс, но он не закрывает PostgreSQL runtime-проверки, G1 или G2.

## Решение

Заменить неоднозначный G0 двумя явными допусками и различать engineering checkpoint и полное завершение WORK:

### G0-OFFLINE

Разрешает только перечисленные в `offline_checkpoint.task_ids` этапы WORK-02—WORK-09. Нужны принятая базовая архитектура, локальные/синтетические входы и отсутствие внешних ingestion-запросов. Офлайн-режим запускается явно, применяется по умолчанию в test/CI, и принудительно отключает ingestion egress в FetchGateway, workers, schedulers, parser subprocess и browser renderer. Fake/mock транспорта разрешён для contract tests.

G0-OFFLINE сам по себе не разрешает доступ к банковским сетям, импорт реальных оригиналов, работу с живым корпусом или публикацию синтетических фактов. Успех checkpoint подтверждается кодом/отчётом и evidence; он не меняет `WORK.status` на DONE и не удовлетворяет G1/G2.

### G0-LIVE(source)

Отдельный допуск на точный источник и цель запроса. До первого автоматического запроса уполномоченный ответственный фиксирует в SRC-001/SourceAcceptanceManifest точные scheme/host/path и допустимые redirects, связь источника с банком, robots, применимые terms, подтверждённое основание получения, разрешённые хранение и повторное использование bytes/extracted data, цели, частоту/лимиты и срок/отзыв допуска. Решение владельца проекта само по себе не является разрешением банка. Неясность, отсутствие evidence или истёкшее/отозванное решение означает BLOCKED. **На дату принятия ADR нет ни одного выданного G0-LIVE.**

Это предварительное разрешение получить данные. После разрешённого получения выполняется отдельная content acceptance: записываются фактические final URL и redirect chain, HTTP/MIME, размер, SHA-256, даты, тип документа, applicability (банк, регион, сегмент, пакет), полнота и ссылки на original. Content acceptance может отклонить документ, не превращая его в evidence и не публикуя факты. Не подменять дату действия датой скачивания, а поиск/snippet — полученным оригиналом.

### Общие обязательные ограничения live-пути

- FetchGateway — единственная точка выхода для ingestion. Он fail-closed проверяет активный source-specific policy до каждого запроса и каждого redirect. Точный host/path должен совпадать с действующим допуском; неизвестный/отозванный источник, неизвестный redirect, невалидная TLS chain, запрещённый адрес или отсутствующий policy дают typed blocked error без сетевого запроса.
- TLS verification никогда не отключать. Проверять DNS/IP и реальный peer IP при соединении и на каждом redirect; блокировать loopback, private, link-local, metadata и локальные IPv6 назначения. Redirect не наследует допуск исходного host автоматически. SSRF меры и egress firewall применяются также к HTML subresources и Playwright; CAPTCHA, авторизация и anti-bot не обходятся.
- Schedulers/workers не обходят Gateway. Проверка выполняется непосредственно перед dispatch и передачей каждого запроса; заранее поставленная job не сохраняет разрешение после его отзыва. Локальное тестирование worker с Fake не является live dispatch.
- Никаких внешних ingestion-запросов в offline/test/CI режиме; ошибка конфигурации означает fail closed. Проверяются также косвенные запросы parser/browser/subresources, а не только основной HTTP client.
- Реальный документ, полученный вручную, допускается только при отдельной записи для ручного получения/хранения/использования, подтверждении происхождения и content acceptance. Если права/условия неясны, не импортировать bytes; источник BLOCKED. Ручной импорт не выдаёт G0-LIVE, не является автоматическим fetch и никогда не засчитывает scheduled-fetch день для G1.
- Синтетические документы, тарифы, банки и метрики маркируются как `synthetic` и хранятся в изолированном test namespace/storage/database. Реальные manifests и публикации отвергают synthetic provenance; test approval не может стать фактом банковского каталога. Синтетические числа нельзя показывать как цены банков.
- Валидация evidence обязательна до одобрения факта: quote/offset/page, immutable extraction/original hash, value/unit/basis/conditions/date/scope; неизвестное остаётся unknown, не конвертируется в ноль или общий scope. Confidence или LLM не заменяют evidence; публикация остаётся ручной и append-only.

## Раннее policy-решение и WORK-16

Для каждого источника решение о допустимости конкретного способа получения, хранения и повторного использования оригиналов/extracted data — часть SRC-001 и обязательная предпосылка G0-LIVE **до получения bytes**. WORK-16 остаётся полной проверкой legal/privacy потоков продукта, retention, удаления, backups и production processing; он не является предпосылкой для офлайн-разработки и не должен создавать цикл `оригинал → G2 → WORK-16 → разрешение на оригинал`. Работа WORK-16 может начинаться как offline inventory/design после собственных технических зависимостей, но production capability остаётся заблокированной до решения ответственного.

Отметка checkpoint DONE не меняет status полного блока.

### G1 и G2

G1 остаётся непройденным, пока для каждого из четырёх банков не подтверждён релевантный официальный документ и не выполнены scheduled-fetch проверки минимум в три разных дня в пределах недели с разрешёнными policy/rates. Ручной импорт не заменяет автоматическое получение. Отчёт NO-GO не равен PASS.

G2 требует реального корпуса документов, human-reviewed gold/tune/holdout, полного существующего набора метрик и порогов ACCEPTANCE_CRITERIA, включая исходное покрытие сравнения. Синтетические fixtures пригодны для разработки/evaluation harness, но не заменяют корпус или знаменатель метрик. Без доказательств фиксируется NOT EVALUATED/NO-GO, а не выдуманный pass.

WORK-10—WORK-19 по-прежнему требуют принятого G2. Офлайн-допуск не снимает эту зависимость и не расширяет scope POC/MVP.

## Последствия и миграция

Обновить синхронно MASTER_PLAN, WORK_INDEX, TASK_INDEX, DEPENDENCIES, EXECUTION_ORDER, POC_SCOPE, WORK-01—09 packages/prompts, связанные task cards/prompts и определения gates/acceptance criteria. Каждый WORK prompt явно задаёт режим `offline` или `live/acceptance`; WORK-02—09 описывают допустимый офлайн-checkpoint и отдельно отложенный live/acceptance scope.

Изменять только документацию и непосредственно затронутые контракты безопасности/evidence; бизнес-логику приложения не менять. Откат возможен восстановлением прежнего dependency/gate описания, но не отключением fail-closed защиты, если реализация уже зависит от неё.

## Проверка

Проверить JSON-синтаксис, уникальность и сохранность исходных task IDs, отсутствие циклов в обоих графах, согласованность статусов и неизменность исходных acceptance criteria. Проверить, что ни один prompt не разрешает live-сеть без source-specific допуска, synthetic корпус изолирован, а G1/G2 сохраняют исходные пороги.
