## A. Логическая архитектура

Сохранить: четыре независимых адаптера, отдельный worker, файловый архив оригиналов, PostgreSQL как единое структурированное хранилище, SQL/FTS, детерминированный Python Comparison Engine, FastAPI, Next.js и заменяемый внешний LLM API. Для 30 сотрудников это достаточный модульный монолит. Логические блоки не становятся микросервисами.

| Наблюдение / пробел в схеме | Риск | Предлагаемое уточнение | Приёмка |
|---|---|---|---|
| «Версии + сравнение изменений» предшествует нормализации | Изменение баннера станет изменением комиссии | Разделить raw-hash, canonical-text-hash и diff опубликованных фактов | Косметическая фикстура не создаёт тарифное событие |
| Архив и БД показаны без протокола согласования | БД ссылается на недописанный PDF | Запись temp → fsync → atomic rename → транзакция метаданных; сверка orphan blobs | Kill в любой точке не создаёт опубликованный факт без оригинала |
| Факты и поисковые фрагменты визуально объединены | Найденный текст принимается за проверенный тариф | Отдельные состояния документа, extraction run и fact; evidence join | Непроверенный факт не попадает в сравнение |
| Показан внешний LLM, но нет границы данных | Утечка чатов и произвольный вызов инструментов | Provider gateway, allowlist read-only tools, структурированный запрос, budget | Инъекция не создаёт сетевой вызов или запись |
| Линии к полному документу не раскрывают авторизацию | Обход ACL через file path | Только document UUID → авторизованный endpoint; локальный архив недоступен напрямую | Чужой приватный документ возвращает 404 |
| «Роли» в PostgreSQL без матрицы доступа | Admin случайно получает всю переписку | RBAC плюс ownership; Admin не читает чужие чаты | Полная cross-user матрица тестов |
| Нет явного мониторинга worker и диска | Платформа незаметно устаревает | Job heartbeat, freshness, disk thresholds, backlog age | Отдельно видны HTTP success и успех обработки |

## B. Мониторинг

Сохранить регулярный обход реестра, ветвление по доступности, архив новой версии, извлечение фактов, ручную проверку и ленту изменений.

1. Проверка HTTP 200 недостаточна: CAPTCHA/страница ошибки может иметь 200. Проверять MIME, размер, банковские маркеры и ожидаемую структуру. Блокировка не обходится.
2. «Контент или редакция изменились?» разделить: ETag/Last-Modified — оптимизация скачивания, SHA-256 — равенство байтов, canonical hash — равенство содержимого. Заголовки не доказывают дату вступления тарифа в силу.
3. Неизменный документ с новым parser version надо переобработать. Это исправление извлечения, а не обязательно банковское изменение.
4. Ветвь «факт однозначный?» должна проверять единицу, базу процента, пакет, регион, сноски и интервал действия. Confidence модели не заменяет проверку.
5. Ручная проверка — отдельная очередь. Кандидат не должен сходиться с одобренной веткой до решения аналитика. Сохранение кандидата допустимо, публикация — нет.
6. Сравнивать факты одного смыслового ключа и контекста. Пропуск строки парсером не равен отмене тарифа; disappearance вызывает review.
7. Подтверждение новой редакции, публикация набора фактов, повышение corpus revision и создание change_events выполняются одной транзакцией. Уведомления доставляются после commit с дедупликацией.
8. Ежедневная проверка не даёт гарантии обнаружения в реальном времени. Proposed SLA — в течение 24 часов после доступной публикации плюс время проверки аналитиком.

## C. Вопрос → ответ

Сохранить аутентификацию, историю, structured intent, PostgreSQL retrieval, Python comparison, объяснение и источники.

1. Память содержит выбранный банк и критерии, но не авторитетные значения. На каждом вопросе заново получить факты на `as_of` и `corpus_revision`.
2. «Найдены сопоставимые источники?» — проверять отдельно для каждой ячейки и пары. Один хороший документ не делает всю таблицу доказанной.
3. Comparison Engine возвращает `better/worse/equal/not_comparable/insufficient/conflict/stale`, формулу и ссылки обеих сторон. Не обязан найти преимущество Сбера.
4. Вход LLM — ограниченный evidence bundle. Выход — структурированные claim IDs. Backend строит цифры, таблицы, даты и ссылки из БД. Простая проверка существования URL недостаточна: URL может вести к реальному документу, который не подтверждает вывод.
5. Произвольная естественная речь не поддаётся полной детерминированной проверке. В MVP фактические предложения формируются шаблонами из проверенных claims; LLM выбирает порядок/тип объяснения и может предлагать формулировку только в контролируемых рамках. Свободный содержательный текст, не сопоставимый claim, отвергается с fallback.
6. Если LLM недоступна, таблица и доказательства сохраняются, пояснение выдаёт шаблон. При невозможности понять намерение — уточнение пользователя, а не предположение о тарифах.
7. PDF открывается целиком с `#page=N`, где N — физическая 1-based страница. Печатный номер страницы хранится отдельно. HTML получает реальный section label или null.

## Решения для согласования

Предлагаются: staging/review/publication внутри того же монолита; job leases и outbox в PostgreSQL; консервативная модель актуальности; контролируемые фактические фразы; расширение схемы таблицами provenance. Причина каждого изменения — проверяемая целостность и доказательность. См. ADR-001…005. Замена стека, внешний поиск в момент ответа, vector DB и обработка закрытых договоров не включены.
